## Project

InsightLens: upload a CSV, get an automatic exploratory data analysis (EDA)
report with charts and plain-language insights.

Goal: a polished portfolio product that shows full stack skills (Next.js,
Node, MongoDB) and data analysis skills (Pandas, statistics) together.
Keep the scope small and the quality high. The frontend is the showcase.

Author: Leon. All code must be understandable and explainable by the author.
Prefer simple, readable solutions over clever ones.

## Architecture

```
Next.js (frontend/)  -->  Express API (backend/)  -->  MongoDB
                               |
                               +--> child_process --> Python (analysis-engine/)
                                                      Pandas EDA -> JSON on stdout
```

Flow:

1. User uploads a CSV. API saves it to backend/uploads/ with Multer, creates a
   Dataset document with status "processing", and responds 202 immediately.
2. API runs the Python script in the background with the file path.
3. Python returns a single JSON report on stdout. API validates it with Zod,
   saves it as a Report document, sets Dataset status to "ready" (or "failed"
   with an error message), and deletes the uploaded file.
4. Frontend polls the dataset status, then renders the report.

## Local environment (no Docker)

- OS: Windows, terminal: cmd. Scripts and instructions must work there.
- MongoDB: local instance or MongoDB Atlas, via DATABASE_URL.
- Python: analysis-engine has its own virtual environment
  (analysis-engine/.venv). PYTHON_BIN in backend/.env points to that venv's
  Python executable, e.g. ../analysis-engine/.venv/Scripts/python.exe
- Each of frontend/ and backend/ has its own package.json and .env.example.
- Do not add Docker or docker-compose.

## Backend (backend/)

Follow BACKEND_STRUCTURE.md exactly: folder layout, file naming, layers,
response shape, error handling, rules and definition of done.
Project-specific decisions:

- Modules:
  - auth/ (login, refresh-token, change-password, log-out, plus
    POST /auth/register for self sign-up with Zod validation)
  - entity/users/
  - dataset/dataset/ upload, list (paginated, search by name), get, delete
  - dataset/report/ get report by dataset id
- Every dataset and report belongs to a user; services always filter by
  req.user.\_id so users never see each other's data.
- File uploads: Multer to uploads/ only. No S3 storage, so omit
  @aws-sdk/client-s3 and the storage helper functions. Adapt the file filter
  to accept .csv only, max 50MB.
- Python runner: src/helpers/analysisRunner.ts spawns the script with spawn
  (not exec), passes the file path as an argument, enforces a timeout,
  captures stdout/stderr, and parses the JSON. Values come from config:
  PYTHON_BIN, ANALYSIS_SCRIPT_PATH, ANALYSIS_TIMEOUT_MS.
- Validate the Python output with a Zod schema matching docs/report_schema.md
  before saving.
- Always delete the uploaded file after analysis, on success and failure.
- Rate limit uploads per user (express-rate-limit).
- A public GET endpoint serves demo reports built from sample-data/ so
  visitors can try the app without signing up.

## Analysis engine (analysis-engine/)

Python 3.11+, Pandas, NumPy only. No other analysis libraries.

- Read CSV robustly: detect delimiter and encoding, handle bad lines.
- For large files, compute heavy statistics (correlations, histograms) on a
  seeded sample of up to 200k rows; state in the report when sampling was used.
- Keep the report compact (well under MongoDB's 16MB document limit):
  binned histograms, top-N categories, at most 100 preview rows.
  Report contents:
- Overview: rows, columns, memory, duplicate rows, overall missing percentage,
  column type counts
- Per column: inferred type (numeric, categorical, datetime, boolean, text, id),
  missing count/percent, unique count, and type-specific stats:
  numeric (mean, median, std, min, max, quartiles, skewness, outliers via IQR,
  histogram bins), categorical (top values with counts), datetime (range,
  counts by month)
- Missing value summary by column
- Correlation matrix for numeric columns (Pearson), plus top correlated pairs
- Insights: rule-based, plain English, each with severity (info, warning,
  critical), the columns involved, and the numbers behind it. Examples:
  high missing rate, likely ID column, constant column, strong correlation,
  heavy skew, many outliers, high-cardinality categorical, possible duplicates,
  datetime column stored as text
- Data preview (first 100 rows)
  Thresholds for insights live in one config dict, not scattered in code.
  Use pytest with small fixture CSVs for type inference, stats and insight rules.

## Frontend (frontend/)

Next.js (App Router), TypeScript strict, Tailwind CSS, shadcn/ui,
TanStack Query, Recharts, react-dropzone, lucide-react icons.
Framer Motion only for subtle transitions.

Pages:

- Landing: clear value proposition, a live demo link, short how-it-works
- Login / Register
- Datasets: list with status badges, search, delete, empty state
- Upload: drag-and-drop with file validation, upload progress, then a
  processing state that polls until ready
- Report (tabs): Overview, Insights, Columns, Missing Values, Distributions,
  Correlations (heatmap), Data Preview (paginated table)
- Public demo report pages for the sample datasets

Design quality is a primary requirement:

- Modern analytics SaaS look: calm neutral palette, one accent color,
  generous whitespace, strong typographic hierarchy, consistent spacing
- Light and dark mode, both deliberately designed
- Fully responsive down to mobile width
- Every async view has loading skeletons, empty states and error states
- Charts: consistent theme, readable labels, tooltips, no default-looking charts
- Accessible: keyboard navigation, focus states, sufficient contrast, labels
- Numbers formatted consistently (thousands separators, percentages, units)
- No placeholder text, lorem ipsum or fake testimonials

Auth on the frontend: access token in memory, refresh token in the httpOnly
cookie set by the API; requests use credentials and retry once after refresh.
All API calls go through one typed API client module.

## Code standards

- TypeScript strict everywhere; type hints and short docstrings in Python
- Comments only where intent is not obvious; no emojis anywhere
- Secrets and paths only through config/env; .env.example in frontend/ and backend/
- No unused code, TODO stubs or commented-out code
- Small focused components and functions

## Testing

- Python: pytest for type inference, statistics and insight rules
- Backend: the definition-of-done checks in BACKEND_STRUCTURE.md, plus
  ownership checks (user A cannot read user B's dataset) and a
  failed-analysis path
- Frontend: Vitest for formatting utilities and key components
